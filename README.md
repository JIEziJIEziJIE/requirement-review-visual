# 需求审查可视化版 · 使用说明

当前仓库标准版 **2.4.1**。保留一级 8 项快筛、二级 12 维深审；默认交付可编辑 Markdown 与单文件离线 HTML。**没有自动修复、自动重试选项是设计约束，不是待补功能。**

## 1. 前 60 秒：给材料，说目标，看结果

直接在对话中说，无需写 JSON 或运行脚本：

> 用需求审查可视化版看这份需求能否提交评审。材料是附件《会议室预约需求 v1.docx》。

没有附件时，也可粘贴正文。以下仅为虚构的最小材料示例，不代表真实系统规则或完整需求：

> 目标：判断能否提交评审。材料：会议室预约需求 v1（粘贴正文）。员工选择会议室和时段后提交；预约成功显示预约记录。取消条件、重复提交结果尚待确认。请基于这些文字审查，不补猜规则。

**会得到什么**：本轮目标对应的结论、待确认问题与责任对象、材料读取范围，以及默认的 Markdown 报告和 HTML 达标卡；明确要求完整深审时生成雷达图。材料片段只能得到局部审查，全部不可读时不出正常评分或准入结论。可以说“只出 Markdown”“只出 HTML”“不落盘”。

下一步可以直接回复“回填 Q1：……，只更新受影响项”；默认不改文件。文件保存位置在写入前确定：指定目录优先，否则识别实际桌面；目录必须已存在，失败不自行换目录或改名。

### 按角色选择阅读路径

- **普通使用者**：先用上面的指令；需要时看下面的调用表、回填方式和 FAQ，不必先读完整规则或脚本。
- **执行者 / 维护者**：先读 [SKILL.md](SKILL.md) 的路由与边界，再按需读 [材料读取](references/material-handling.md)、[数据与 CLI](references/examples.md)、[错误提示](references/error-codes.md)、[反模式](references/pitfalls.md)。维护自检见 §8。

## 2. 怎么调用

| 你说 | 它做 |
|---|---|
| 这份需求能否提交评审 | 一级产品自检，8 项达标卡 |
| 这份需求能开工吗 | 一级开发快评 |
| 帮我看看这份需求能不能测 | 一级测试快评 |
| 做完整可测性深审，出雷达图 | 二级 12 维深审 |
| 回填 Q1：……，只更新受影响项 | 四小段增量复筛，默认不改文件 |
| 按已确认的 Q1 补文档 | 给章节位置、可粘贴正文、确认依据 |
| 把已确认内容编辑到需求修订副本 | 核对原文、工具与授权后写副本，保存读回 |
| 更新报告和图表，保存 r2 | 同源刷新所请求格式，不覆盖旧报告 |

材料可为路径、附件、链接或正文。按本轮目标选产品/开发/测试，不按职业默认选；目标不清楚才问一次最小问题。一级存在 P0 只建议按需深审，不自动展开二级。

## 3. 输出与可靠性边界

- 首次完整审查默认 Markdown + HTML；两份嵌入同一份结构化 DATA，Markdown 放在末尾注释，便于续审。注释也属于交付内容，不藏不应交付的信息。
- 对话给关键结论、范围和文件入口；完整细节在报告中。HTML 首屏最多 8 项，P0 首屏重点最多 5 项；超出部分可展开，仍参与全部计算。
- 产品确认业务结果，研发确认实现；业务确认、正文生成、文件写入、功能验证分别记录，不能互相代替。
- **指数反映材料明确程度，不是产品质量分或实际测试通过率。** 全不适用不作正常准入判断；部分可读在页面和 Markdown 开头显著标注 `WARN-MAT-01` 局部审查，不代表整份需求通过。
- DATA 校验失败不生成；全部输出统一预检，父目录须已存在。普通生成用 `wx` 独占创建，每个目标单次写入并读回；不覆盖、不换目录、不创建目录、不改名、不修复、不重试。
- I/O 中途失败立即停止后续写入，报告已完成、可能不完整/未验证、未尝试、未触碰文件；保留部分产物，不删除，不称整体成功。详情见 [错误提示](references/error-codes.md)。

报告名称、修订后缀和目录在生成前确定。CLI 使用指定 basename 加 `.md` / `.html`，不在失败后自动另存新名称；已存在同名目标即停止，由用户确认下一轮目标。

## 4. 确认后如何继续

> 回填 Q1：只保留一条预约记录，第二次展示现有记录。只更新受影响项。

这是虚构回复示例，不是预设业务规则。若 Q1 还需要研发确认实现，就不会因此自动关闭或提高分数。

默认只返回：已关闭事项 / 仍待确认事项 / 变更的维度与优先级 / 更新后结论。缺原报告、编号映射或原文时先要必要材料，不猜。

- 说“补文档”：默认给实际章节位置 + 可粘贴正文 + 确认依据，不改文件。
- 明确说“编辑文件/保存修订副本”：仅在对应能力可用、授权有效且原文版本核对通过后，写已确认的相关内容。
- 无权限、能力不支持、版本不符或保存读回失败：停该分支，说明实际状态，不声称写入；可提供可粘贴正文。
- 没有真实功能执行证据，保持“未验证”。

按证据正常首次生成、按需补文档、用户新授权的新一轮操作，不属于失败后的自动修复或自动重试。具体范围见 [材料与组合使用](references/material-handling.md)。

## 5. 对话参数与生成 CLI 是两层

| 对话参数 | 范围 | 默认 |
|---|---|---|
| depth | 1 / 2 | 按目标 |
| lane | product / dev / test | 按目标；深审 test |
| out | 已存在的输出目录 | 实际桌面 |
| format | md+html / md / html | md+html |
| top | 1～8 整数 | 8，仅限首屏 |
| lang | zh / en | zh |

对话支持 key=value、`--no-html` 和自然语言。未知、非法、矛盾参数须提示并问一个最小澄清问题；不默默忽略、不把越界值收敛成合法值、不擅自选保守方案。英文业务内容由执行者翻译，规范编号与状态枚举保留用于一致计算。

**生成 CLI 不是对话参数解析器**：只接收 [命令契约](references/examples.md) 中的语法，未知选项、非法值或多余参数严格拒绝。支持 `--check data.json` 只读检查和 `--help` / `-h` / `help`；没有修复或重试开关。

## 6. 安装、兼容与离线范围

将整个 `requirement-review-visual/` 放入当前平台用户技能目录；WorkBuddy 为 `~/.workbuddy/skills/`。重新加载技能列表或新开会话使用。本仓库为 **2.4.1 标准版**；SkillHub、开放平台等市场版本以各平台实际状态为准，**GitHub 更新不等于其它平台同步更新**。

- Node 推荐 **22 / 24**；本机实测版本 **22.22.2**。脚本零 npm 依赖，不声称已完成所有操作系统、Node 版本或平台组合测试。
- 模板和生成的单文件 HTML 无外部依赖，可离线查看；本地材料可走离线读取能力，具体格式仍取决于环境。在线材料、知识库、在线文档需网络及对应授权，不是“所有操作都无需联网”。
- 生成器输入为严格 UTF-8 无 BOM 的 DATA JSON，最大 **8 MiB**。这是生成 DATA 的保护上限，**不是原始文档大小或页数上限**，不自动裁剪内容。
- schemaVersion 仍为 **2**。v2.4.0 合法完整数据可继续使用；未知键、非字符串可选文本等过去宽松数据会被拒绝。部分读取/读取失败需非空 `coverage`，由执行者依据原材料确认补足，不能自动修复、猜值或让用户手写 JSON。
- v2.3.x 旧 items/dims/todos 须按原材料映射为 checks/findings；不直接复制旧分数，旧报告不自动改写。

## 7. 常见问题

**规则太多，要全部读完才能用吗？** 不必。普通使用者给材料和目标即可；执行者按上面的阅读路径渐进加载，8 项/12 维判定规则不减少。

**发生错误后会自动改数据或再试一次吗？** 不会。失败时给原因、影响、文件状态和可执行下一步；用户明确确认处理范围后才开始新一轮操作，避免改动用户未确认的内容。

**大文档能处理多少页？** 不承诺无限规模或固定页数，也没有可引用的性能基准实测。一次读不完时先列目录/章节清单，再按章节连续读取并记台账；这不是失败后重试。未读完不能下全文结论，不能用随意摘要替代正文；无法完成时说明缺口。见 [大文档策略](references/material-handling.md)。

**能接测试用例或补文档工具吗？** 按“读取来源 → 审查 → 按需写用例/补文档”衔接，传递报告版本、稳定编号、原始标题、证据和未确认项；未确认预期不作事实。工具是否安装、可用、已授权需当次核实。

**同一个 P0，产品与测试结论为何不同？** 产品判断能否提交评审，测试判断能否形成预期结果。产品“补充后提交”不能搬作“测试通过”。

**有答案就会自动涨分吗？** 不会。先核对确认来源，再复筛相关维度；研发未确认事项继续开放。

**输出失败能自动换桌面、改名或清理半成品吗？** 不能。保留现场和分项清单，停止相关环节，等待明确的新操作授权。

**能读写所有在线文档吗？** 不能保证。企业微信文档、腾讯文档等取决于实际连接能力和权限；受限时说明缺口，不绕过授权、不索取凭据。

## 8. 维护者：规则分工与发布自检

规则按职责分层：**SKILL 路由/边界 → review-core 字段/计算 → build-review 写入 → references 细则**。细则不能扩张入口授权，渲染不能覆盖计算，写入不能越过输出保护。发现文字与实现冲突时，停止受影响环节、指出冲突并请求维护确认；不得擅自选一处继续执行。

| 维护时需要什么 | 去哪里 |
|---|---|
| 入口、路由、授权边界 | [SKILL.md](SKILL.md) |
| 8 项 / 12 维业务判定 | [快筛规则](references/fast-screen-rules.md) / [深审规则](references/deep-review-rules.md) |
| 读取台账、覆盖范围、组合使用 | [material-handling.md](references/material-handling.md) |
| DATA、CLI、虚构示例、验收 | [examples.md](references/examples.md) |
| 异常分层与禁止行为 | [error-codes.md](references/error-codes.md) / [pitfalls.md](references/pitfalls.md) |
| 字段校验与派生计算 | [review-core.js](scripts/review-core.js) |
| 同源渲染与文件写入 | [build-review.js](scripts/build-review.js) |
| 计算/渲染回归与 CLI 回归 | [test-review.js](scripts/test-review.js) / [test-cli.js](scripts/test-cli.js) |

每次修改后按下面清单核对，填写当次实际结果；清单本身不代表已经验证或发布：

- [ ] 严格解析 SKILL frontmatter YAML，检查字段、引号和当前版本。
- [ ] 核对 README、CHANGELOG、SKILL、生成器与内置生成模板的版本一致性；不把 schemaVersion=2 改成软件版本号。
- [ ] 检查相对链接和 `assets/icon.png` 实际存在；包内图标不等于线上头像已更新。
- [ ] 比对生成模板与当前引擎/生成器一致性；`--templates` 只用于授权维护固定两个 HTML 模板，不能当作普通生成的覆盖开关。
- [ ] 分别运行 `node scripts/test-review.js`、`node scripts/test-cli.js`，记录实际环境、结果和数量；不得沿用旧数量或猜测新增测试数。
- [ ] 核对未知字段、文本类型、同号重复、coverage、局部限定、编码/大小、预检/写入/读回和失败文件清单等验收项；执行结果另记，不预称通过。
- [ ] 保持 HTML 安全 JSON 数据区与 DOM 文本渲染，Markdown/HTML 同源同版本；不手改显示分数。
- [ ] 示例完全虚构或脱敏，不包含真实需求、内部链接、业务截图或真实反馈，不为评测向外上传真实例子。
- [ ] 明确“不自动修复、不自动重试”；核对帮助、错误提示和参考文件无相反指令。
- [ ] 升级后先完成实际回归与一致性核对；公开发布须另行明确授权，不自动同步远端，不声称未经复评的分数已提升。

## 9. 如何看待反馈

将外部评测与实际使用反馈当作检查线索，而不是正确性证明。只按具体反馈和可复现问题改进，不凭分数臆造缺陷；不为追求分数改变明确设计边界，不承诺分数提高。

真实试用仍需观察：是否能直接回答、责任是否明确、局部范围是否醒目、回复一个事项是否只影响相关部分、正文能否放入正确章节、原件是否受保护、报告与图表是否一致。自动校验不能替代同事试用。
