# 需求审查可视化版 · 使用说明

版本 **2.4.0**。保留一级 8 项快筛、二级 12 维深审；把“发现问题”接到“能回答、能补文档”。默认交付可编辑 Markdown 与单文件离线 HTML，不需要安装图表库或登录。

## 1. 怎么调用

在对话中直接说，不用记命令：

| 你说 | 它做 |
|---|---|
| 用需求审查可视化版看这份需求能否提交评审 | 产品自检，8 项达标卡 |
| 这份需求能开工吗 | 开发快评 |
| 帮我看看这份需求能不能测 | 测试快评 |
| 做完整可测性深审，出雷达图 | 12 维深审 |
| 回填 Q1：……，只更新受影响项 | 四小段增量复筛，默认不改文件 |
| 按已确认的 Q1 补文档 | 给章节位置、可粘贴正文、确认依据 |
| 把已确认内容编辑到需求修订副本 | 具备对应文档能力并核对原文后写副本，保存读回 |
| 更新报告和图表，保存 r2 | 同源刷新 Markdown/HTML，不覆盖旧报告 |

材料后附路径、附件、链接或正文即可。按本轮目标选产品/开发/测试，不根据你的职业默认选。目标不清楚才问一次 A/B/C/D。

## 2. 这版具体改善什么

- **说得懂**：先问“用户应该看到什么、产生几条记录”，技术术语保留在研发备注。
- **分得清**：产品确认业务结果，研发确认实现；产品回答不等于研发方案已经确认。
- **接得上**：按原编号回填，只复筛受影响部分；需要时再补正文、授权后写修订副本。
- **不重复填数字**：数量、达标率、综合指数、结论和颜色从同一份检查结果计算。
- **先看下一步**：先呈现结论、谁来确认、该回答什么、补到哪里，再看达标卡或雷达图。
- **不把确认当验证**：业务确认、正文生成、文件写入、功能验证分别显示。

保留研发视角、8 项/12 维、证据要求和离线能力。没有新增在线工作台、账号体系或强制操作步骤。

## 3. 正常会拿到什么

首次完整审查默认两个文件。你可以说“只出 Markdown”“只出 HTML”“不落盘”。

| 级别 | Markdown | HTML |
|---|---|---|
| 一级 | 需求名-快筛-YYYYMMDD.md | 需求名-快筛达标卡-YYYYMMDD.html |
| 二级 | 需求可测性审查_简称_YYYYMMDD.md | 需求名-可测性雷达图-YYYYMMDD.html |

保存到实际桌面，指定目录优先；修订增加 r2 等后缀。HTML 和 Markdown 均保留同一份结构化审查数据（Markdown 放在末尾注释），之后可拿任一原报告继续回填，不需要手工整理 JSON；仅包含该报告允许交付的内容。

对话给关键结论和文件入口；完整细节在报告中。HTML 首屏默认最多 8 项，P0 重点最多 5 项；超出的保留在展开区，并参与所有计算，不会因为显示不下就丢掉。

**指数反映材料的明确程度，不是产品质量分，也不是实际测试通过率。** 全部不适用或材料完全不可读时不作正常准入判断。

## 4. 确认后如何继续

最短操作：

> 回填 Q1：只保留一条预约记录，第二次展示现有记录。只更新受影响项。

这里只是虚构的回复示例，不是系统预设的业务规则。若 Q1 还需要研发确认实现，就不会因此自动关闭。

默认只返回：已关闭事项 / 仍待确认事项 / 变更的维度与优先级 / 更新后结论。缺少原报告、编号映射、原文时先要必要材料，不猜。

### 补文档是可选项

- 说“补文档”：先给实际章节位置 + 可粘贴正文 + 对应确认依据，默认不改文件。
- 明确说“编辑文件/保存修订副本”：转给当前可用的文档能力，仅改已确认相关段落，优先副本。
- 没权限、工具不支持、版本对不上或保存失败：明确说明，不声称写入，仍可提供可粘贴正文。
- 没有真实功能执行证据，始终标“功能未验证”。

## 5. 可选参数

| 参数 | 范围 | 默认 |
|---|---|---|
| depth | 1 / 2 | 按目标 |
| lane | product / dev / test | 按目标；深审 test |
| out | 输出目录 | 实际桌面 |
| format | md+html / md / html | md+html |
| top | 1～8 | 8，只限首屏 |
| lang | zh / en | zh |

支持 key=value、--no-html、自然语言。英文业务内容由执行者翻译，规范维度编号与状态枚举保留用于一致计算；不是自动机器翻译整份需求。

## 6. 安装与更新

将整个 `requirement-review-visual/` 放入当前平台的用户技能目录；WorkBuddy 为 `~/.workbuddy/skills/`。重新加载技能列表或开启新会话后使用。若从市场安装，公开版本是否已经更新以市场实际状态为准；**本地升级不等于自动公开发布**。

v2.4.0 内部 DATA 改为 schemaVersion=2，旧模板数据不能直接粘进新模板。已有旧报告不自动改动；需要继续回填时按原报告、原材料映射并补齐缺失依据，不能只复制旧分数。

## 7. 目录与维护

- `SKILL.md`：入口、路由、契约、自检。
- `references/fast-screen-rules.md`：8 项标准与三链路判定。
- `references/deep-review-rules.md`：12 维、建议八要素、报告八节。
- `references/material-handling.md`：读取、答案回填、按需补文档。
- `references/examples.md`：数据字段、完整虚构示例说明、试用验收清单。
- `references/pitfalls.md` / `error-codes.md`：常见错误与异常说明。
- `templates/`：两种 Markdown 结构与两种可直接离线打开的 HTML 示例。
- `scripts/review-core.js`：校验、统计、分值与链路结论。
- `scripts/build-review.js`：同源双输出与安全序列化。
- `scripts/test-review.js`：无第三方依赖回归验证。

普通使用者不需操作 scripts。维护者使用可用的 Node（支持 ES2022），无需安装 npm 包；生成输出前确保目录已存在。详细命令见 references/examples.md。

HTML 用安全 JSON 数据区与 DOM 文本节点，支持尖括号等原文文本，不把需求内容当 HTML 执行。不要手工拼脚本，不要单独改显示分数。

## 8. 常见问题

**有 P0 就必须做深审吗？** 不必。先关闭关键口径也可以；只建议深审，不强制自动出长报告。

**同一个 P0，产品与测试的结论为什么不同？** 产品判断能否提交评审，测试判断能否形成预期结果。产品“补充后提交”不能搬作“测试通过”。

**反馈说术语看不懂，是删掉技术检查吗？** 不是。研发视角保留，只把问题翻译成能回答的业务结果，实现细节归研发。

**有答案就会自动涨分吗？** 不会。必须核对确认来源，复筛相关维度；技术未确认的事项仍开放。

**能读所有文件并修改所有在线文档吗？** 取决于当前环境的读取、编辑能力和授权。不具备时会说明并建议导出件或可粘贴文本，不绕权限。

**出现异常怎么办？** 说明发生了什么、影响哪些结论、下一步怎么做。数据不一致时不展示正常分数，不让用户看到貌似正常的错误图表。

## 9. 下一轮同事试用

优先检查：不经作者解释能否读懂、能否直接回答、是否清楚谁负责、回复一个事项能否只更新相关部分、确认正文能否放进正确章节、原件是否受保护、图表与报告是否一致。使用虚构或脱敏材料，不把真实业务内容收进公开技能包。
