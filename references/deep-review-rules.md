# 二级深审 · 完整规则

跑二级深审时读本文件。主文件 `SKILL.md` §3.2 定义计算与结论，本文件保留 12 维、八要素和报告结构。所有面向产品的问法先说业务结果；实现方案交研发确认。

---

## 1. 核心原则（7 条）

1. **先取证，后判断**：每条建议关联原文、截图、页面区域、接口字段、原型节点或明确标注的材料位置；
2. **区分事实与推断**：材料写出的称"已明确"；未覆盖的称"待确认"；上下文推测必须标注"推断"，不得写成既定规则；
3. **不替需求方拍板**：不擅自补充价格、时间、权限、阈值、状态、文案、接口码或业务规则；
4. **关注可测性，不评价个人**：评价需求表达、规则完整性和验收条件，不评价人；
5. **措辞专业且便于协作**：用"建议调整/明确/补充/统一/确认""待进一步对齐""优先级"；
6. **结论要可行动**：每条建议说明影响范围、建议动作和确认对象；
7. **宁可保留不确定，也不制造确定性**：识别不清就保留原样列入待确认。

---

## 2. 预处理：需求证据台账

正式审查前建立（不必全部展示）：

- 材料清单：来源、名称、类型、版本/时间、读取状态；
- 章节/页面/画板索引（便于引用定位）；
- 业务对象：用户、订单、会员、试卷、学生、活动、任务等；
- 操作与角色：谁在什么前置条件下执行什么动作；
- 字段与规则：输入、输出、必填、枚举、默认、计算、展示；
- 流程与状态：开始、进行中、成功、失败、取消、过期、回退、终止；
- 外部依赖：登录、支付、短信、内容服务、第三方平台、设备、权限、接口；
- 验收证据：数字指标、页面结果、接口结果、数据落库、消息通知、日志或截图；
- 变更记录：新增、修改、删除内容以及受影响范围。

链路模板：**需求原文 → 业务规则 → 可验证条件 → 建议测试范围**，确保每条建议可追溯。

## 3. 12 个可测性维度

逐项检查。没有明显缺口时写"当前材料未发现需要补充之处"，**不为了凑数量制造建议**。

1. **目标、范围与成功标准** — 目标用户、业务目标、实现范围、非目标、上线范围、成功指标、验收对象；拦截"提升体验、方便使用、提高转化、支持多端"等不可验证表达。
2. **术语、文案与规则口径** — 同一概念是否多种叫法、数字/单位/时间格式是否一致、展示文案与后台规则是否一致、图文是否冲突；保留原文引用，不判定哪处正确。
3. **角色、权限与前置条件** — 登录状态、账号类型、组织/学校/班级范围、会员等级、角色权限、数据归属、设备/渠道、开关、前置数据；覆盖正常授权、无权限、权限变更、账号冻结/注销。
4. **主流程与业务规则** — 拆为可执行动作，核对触发条件、处理顺序、计算规则、展示结果、保存时机、完成条件；检查规则可否组合、是否互相覆盖或优先级未说明。
5. **边界、容量与精度** — 数量上下限、长度、文件大小、金额与小数位、时间边界、分页、并发、重复操作、空值、极端字符、跨天/月/年、闰年、时区；未给出的阈值必须标待确认。
6. **异常、失败与可恢复性** — 网络中断、超时、服务异常、第三方失败、空数据、数据不存在、重复提交、部分成功、回调乱序、刷新/返回、重试、取消、回滚、降级、幂等、错误提示、人工补偿。
7. **状态流转与数据一致性** — 对象状态、合法转换、触发事件、终态、回退路径、重复事件、并发修改、刷新后状态、跨端同步、最终一致性；图中箭头不能替代文字规则。
8. **数据结构、输入输出与接口** — 字段定义、类型、必填/选填、默认值、唯一性、枚举、格式、编码、排序、过滤、分页、协议、错误码、幂等键、敏感字段、脱敏、存储与展示映射。
9. **兼容性与非功能要求** — 浏览器/客户端/系统版本、分辨率、设备、渠道、网络、性能、并发、可用性、安全、隐私、审计、日志、监控、国际化、无障碍；仅在范围涉及或可由材料确认时提出。
10. **页面、交互与视觉状态** — 入口、返回、跳转、加载、空状态、错误状态、禁用、选中、悬浮、弹窗、遮罩、键盘、滚动、超长文案、重复点击、断点续作、不同权限下的展示。
11. **外部依赖、运营配置与发布窗口** — 依赖系统、配置后台、内容/素材、支付、消息、审核、渠道包、开关、定时任务、缓存、数据初始化、发布顺序；检查测试环境与生产配置是否可能不一致。
12. **验收、回归与可观测性** — 每项需求有可判定预期结果、验收数据、证据留存方式、日志/埋点/监控、回归范围、发布准入条件；没有验收依据时给出可执行补充方向，不擅自填指标。

## 4. 建议条目的写法

每条使用"**建议 NNN**"，**不使用"问题 NNN"**。每条八要素齐全：

| 要素 | 说明 |
|---|---|
| 优先级 | P0 / P1 / P2 / P3 |
| 建议类型 | 目标范围 / 口径一致性 / 边界条件 / 异常处理 / 状态流转 / 权限前置 / 数据规则 / 外部依赖 / 交互视觉 / 非功能 / 验收与观测 |
| 依据位置 | 章节、页码、表格、画板/页面、截图区域、接口字段或原文摘录 |
| 当前材料表现 | 只描述事实，必要时并列不同材料 |
| 建议调整 | "建议明确……""建议补充……""建议统一……""建议确认……" |
| 对测试工作的影响 | 影响哪些用例、断言、数据、环境、回归范围 |
| 待确认对象 | 产品/运营/设计/研发/业务/数据，材料能判断时才填 |
| 确认状态 | 按所需业务/研发答案与来源推导为待确认 / 部分确认 / 已确认；缺证据继续待确认 |

保留八要素并补入稳定编号、关联维度、产品问题、研发问题、建议补充位置。技术细节放“给研发的备注”。所有需要的确认都完成才关闭；产品回复不得自动关闭技术项。关闭记录保留，不重新编号；文档与功能验证另行记录。

---

## 5. 优先级定义

| 级别 | 含义 |
|---|---|
| P0｜发布前必须对齐 | 核心流程无法判定、资损/数据错误/权限风险、主流程无法执行或验收结论无法成立 |
| P1｜建议在开发或用例设计前明确 | 明显影响分支覆盖、接口联调、状态一致性、回归范围或跨角色理解 |
| P2｜建议在本轮完善 | 影响边界覆盖、体验一致性、配置正确性或问题定位效率 |
| P3｜可纳入后续优化 | 表达清晰度、文档维护性、低频体验和可观测性增强项 |

证据不足时降低断言强度并标注"待确认"。

---

## 6. 结论三档（固定用词）

- **当前材料可支持用例设计**：核心范围、主流程、关键规则、权限、异常和验收证据基本明确，剩余内容不影响主要断言；
- **补充确认后可支持**：存在 P1/P2，确认或补充材料后可进入用例设计；
- **需要先完成关键口径对齐**：存在一个或多个 P0，或核心对象/流程/结果/权限/验收标准不能形成可执行断言。

结论后必须写出进入下一阶段的条件。计算真源为 scripts/review-core.js：有未关闭 P0 或未取整均值 <70 → 第三档；均值 ≥85 且无 P0/P1 → 第一档；其他均值 ≥70 且无 P0 → 第二档。高均分不能掩盖 P1；展示取整不能跨阈值改判；全部不适用不评分、不判通过。

指数只表示当前材料明确程度，不是产品质量分、代码质量分或功能测试通过率。

---

## 7. 报告结构（八节）

模板见 `templates/deep-review-report.md`。八节固定：

1. 审查概览（来源、材料范围、日期、指数、优先级分布、结论）
2. 整体判断（1～3 段，只引用已读证据）
3. 建议调整清单（建议 NNN，八要素）
4. 按审查维度汇总（12 维表格：成熟度、分值、主要影响）
5. 待确认事项（`- [ ]` 可勾选）
6. 建议补充的验收证据（6 类）
7. 测试准备提示（含进入下一阶段的条件）
8. 材料与证据索引

## 8. 语言规范

**推荐**：
- "建议进一步明确……，便于各角色基于同一口径验收。"
- "当前材料已描述主流程，异常场景的处理方式建议补充。"
- "该处与另一材料存在口径差异，建议确认以哪一版本为准。"
- "若该规则已在后台或接口中固化，建议补充字段/配置说明作为验收依据。"
- "为降低回归遗漏，建议将历史反馈转化为可执行的检查项。"

**避免**：
- "问题清单""问题 XXX""严重等级"；
- "需求写得不行""明显错误""不合格""谁漏了"；
- 没有证据支持的"必然""一定""系统无法"；
- 将建议值写成已确认值；
- 将测试侧建议写成产品最终方案。
