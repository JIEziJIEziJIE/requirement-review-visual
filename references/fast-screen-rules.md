# 一级快筛 · 完整规则

跑一级快筛时读本文件。主文件 `SKILL.md` 的 §3.1 只给了 5 步流程，细则在这里。

---

## 1. 8 项最小标准

每项只回答**四档之一**：已明确 / 部分明确 / 未明确 / 不适用。并给一句可行动建议。

### 1.1 目标与范围
确认：为什么做、给谁用、本期做什么、不做什么、覆盖哪些端/渠道/角色。
拦截：只有背景和价值没有交付范围；"优化体验、提升效率、全渠道支持"等无法判断的表述。

### 1.2 主流程与完成标准
确认：入口、前置条件、关键操作顺序、成功结果、结束条件和返回路径。
拦截：只能看懂页面，不能还原从开始到完成的完整路径。

### 1.3 业务规则与关键数据
确认：计算、价格、时间、数量、状态、字段、枚举、默认值、数据来源和展示结果。
拦截：金额、权益、资格、排序、优先级、有效期等影响结果的规则依赖猜测。

### 1.4 角色、权限与前置条件
确认：登录状态、用户类型、角色权限、组织/数据范围、会员/渠道资格、必要配置和前置数据。
拦截：只写"需要登录"或"按权限展示"，不说明不同身份看到什么、能做什么。

### 1.5 异常与边界
至少确认：空数据、重复点击/提交、网络异常、接口失败、超时、取消、刷新返回、活动前后、数量/金额/时间边界。
拦截：只有正常流程；失败后结果、提示、重试、回滚或补偿没有规则。

### 1.6 状态与数据一致性
确认：核心对象有哪些状态、如何变化、谁触发、刷新/重试/跨端后是否一致。
拦截：支付、订单、任务、审批、会员权益等对象没有状态闭环；页面成功不等于数据成功。

### 1.7 依赖与交付条件
确认：接口、后台配置、第三方服务、素材、定时任务、开关、环境、发布顺序、缓存和回滚依赖。
拦截：写了功能目标，但没说明谁提供依赖、何时可用、如何验证、失败怎么办。

### 1.8 验收与可追溯证据
确认：每项核心需求的预期结果、验收数据、页面/接口/数据库/日志/埋点证据、回归范围。
拦截：只写"完成开发""效果良好"，无法判断什么结果算完成。

## 2. 三链路固定结论词（**不得自造**）

### 2.1 产品自检链路

结论三选一：**可提交评审** / **建议补充后提交** / **暂不建议提交**。

输出顺序：
1. 需求自检结论（三选一，不并列候选）；
2. 逐项 8 项标准；
3. "建议补充……"列出最多 5 个关键缺口；
4. 每个缺口补：影响对象、建议写入位置、需产品确认的规则；
5. "提交前最小补充清单"，只留会影响开发、测试或验收的。

推荐要素：需求自检结论 / 当前已明确（2～5 项关键事实）/ 提交前必须补充（P0/P1）/ 可后续完善 / 建议补充位置。

**重点是帮助把需求写到可交付，不是评价文档好坏。**

### 2.2 开发快评链路

结论三选一：**可以进入开发** / **补充确认后可以开发** / **暂不建议直接开发**。

必查六项：
- 本期做什么和不做什么；
- 入口、主流程和完成条件；
- 核心规则、字段、接口输入输出和状态；
- 用户资格、权限和前置配置；
- 失败、重试、幂等、回滚或降级处理；
- 外部依赖、环境、配置、发布和验收方式。

判"暂不建议直接开发"时，必须列出开发前需关闭的事项，不给抽象评价。

### 2.3 测试快评链路

结论三选一：**具备初步可测条件** / **补充确认后可测** / **暂不具备初步可测条件**。

必查六项：
- 能否列出主流程和关键分支；
- 能否准备不同角色、权限、状态和边界数据；
- 能否对页面、接口、数据库、消息、日志或埋点形成断言；
- 能否判断成功、失败、取消、超时、重复操作和恢复结果；
- 能否明确时间、金额、数量、排序、状态等边界；
- 能否确认测试环境、依赖服务、配置和回归范围。

必须区分三类：
- **已明确**：原文能直接支持的事实；
- **待确认**：文档没给出或存在多种解释；
- **推断**：上下文推测，不能作为最终断言。

在 8 项标准表中：能形成断言写"已明确"；待确认或只能推断写"部分明确"或"未明确"，并在"建议明确"列落成 Q 编号问题。

### 2.4 三类结论互不推导

- 产品结论回答"需求是否具备提交评审基础"；
- 开发结论回答"是否具备唯一、基本完整的实现条件"；
- 测试结论回答"是否能形成初步测试范围、数据和预期结果"。

不能因为"可提交评审"就自动判"可以开发"，也不能因为"可以开发"就自动判"具备完整可测性"。

## 3. 优先级与判定规则

只用"优先级"，不用"严重等级"。

| 级别 | 含义 |
|---|---|
| P0｜必须先确认 | 影响核心范围、金额/权益、权限、数据正确性、核心状态、主流程实现或验收结论 |
| P1｜建议尽快明确 | 影响分支覆盖、接口联调、异常处理、回归范围或跨角色理解 |
| P2｜本轮完善 | 影响边界覆盖、体验一致性、配置核对、日志和问题定位，但不阻塞初步判断 |

判定：
- 有 P0 → 不能判"可以进入开发"或"具备初步可测条件"；
- 无 P0 有 P1 → 通常判"补充确认后可以开发/可测"；
- 只有 P2 → 可进入初步评审或开发准备；
- 不凑数量，无明显缺口时写"当前材料未发现关键缺口"。

### 3.1 产品自检链路有 P0 时怎么选（原规则未覆盖，按此判）

产品自检的两个否定档是**建议补充后提交**和**暂不建议提交**，二选一：

| 情况 | 选 |
|---|---|
| P0 都是"填口径"性质（补数字、统一时间、补状态定义），目标与主流程仍成立 | **建议补充后提交** |
| P0 涉及方案本身要重做（目标不成立、主流程走不通、核心规则与其他需求冲突） | **暂不建议提交** |
| P0 在评审前确定无法关闭 | **暂不建议提交**（并在报告写明改判原因） |

选"建议补充后提交"时，必须同时写明一句"若 P0 在评审前无法关闭，应改判暂不建议提交"，避免评审照常开了却拿不到有效结论。

---

## 4. 长度上限

- 8 项标准固定 8 行；
- 待确认事项不超过 8 条，P0 不超过 5 项；
- 末尾问题清单不超过 8 条；
- 超出时只保留优先级最高的。

---

## 5. 何时转二级

出现以下任一，在报告末尾写"建议进入二级深审"并说明原因：
- 出现 P0；
- 用户明确要求详细审查、完整评审、可测性报告、分析所有风险；
- 材料跨多来源且存在口径冲突；
- 一级通过后用户要继续写用例但关键口径仍待确认。

未出现以上情况，不主动输出二级报告。
